# Implementation status and engineering decisions

## What is complete

The portfolio MVP now includes Frontend Intelligence Engine as its primary developer experience. It remains one modular-monolith system with an Electron desktop, browser UI, API, analysis worker, performance runner, an optional VS Code companion, and an optional read-only MCP adapter. Electron manages the canonical services and native acquisition rather than introducing a second analyzer. The MCP adapter exposes bounded completed evidence rather than creating an agent or mutation path. The durable architecture path has been exercised with a real PostgreSQL database: archive upload, leased job, AST graph generation, Prisma persistence, impact query, and immutable source preview. Static results remain useful with no AI configuration, and measured performance remains separate from static risk signals. The trusted Observatory frontend also has reproducible Lighthouse lab and Rollup bundle evidence.

“Complete” here means the requested vertical slices exist and their core path is verified. It does not mean every production hardening item in the Phase 1 roadmap is finished.

| Separate performance process and explicit load models    | Load generation can starve an API; k6 VUs and autocannon connections are not the same unit                | In-process load is simpler but corrupts both API availability and measurement                                                          | Container/cgroup isolation, distributed runners, signed target authorization, DNS rebinding/redirect revalidation   | Controlled real autocannon run, target-policy tests, requested/achieved metrics, explicit k6-unavailable state    |

## Known limitations / next production tranche

- Authentication, authorization, true multi-tenancy, PostgreSQL row-level security, quotas, audit-actor identity, and hosted secret management are not implemented.
- GitHub acquisition supports public repositories or a configured token; a GitHub App OAuth/installation/permission lifecycle is not implemented. The desktop token path is appropriate for one trusted local operator, not hosted multi-user authorization.
- Browser local-folder packaging is capped at 5,000 files and 50 MB of selected source. Electron raises the source boundary to 20,000 files and 150 MB, while both still enforce 5 MB per file and 25 MB compressed. Repositories beyond those limits need a streamed or explicitly raised-policy path.
- V1 dependency advisory lookup supports the root npm `package-lock.json`; pnpm/yarn/bun lock parsers remain unassessed.
- Static graph resolution does not yet cover external Angular HTML templates, every custom router/state/API wrapper, runtime DI, reflection, or full GraphQL schema/data flow. Named GraphQL operations and common framework calls are covered.
- Connected-repository bundle size remains explicitly unmeasured because uploaded code is not built. The Observatory application itself now has bundle reports. Large-import and lazy-loading findings for uploaded projects remain review candidates, not fabricated byte estimates.
- The graph currently uses deterministic lane layout. Large enterprise graphs need clustering, incremental analysis, layout workers, and saved scopes.
- Backend/database rules do not yet implement full interprocedural request-path analysis, SQL AST/query plans, migration drift, auth guard conventions, or real response-size measurement.
- Running performance jobs cannot currently be cancelled; cancellation is accepted only while queued. k6 must be installed separately. Redirect-by-redirect DNS validation and container-level process cleanup still need hardening.
- AI adapters compile against pinned SDKs and share a validated output contract, but live external-provider calls were not executed without user credentials. Ollama was also not running in the final environment.
- The dashboard is dark-theme only and needs broader keyboard/focus/contrast/reduced-motion plus automated graph-interaction browser coverage before a public release.
- The VS Code companion is built and command-complete but is not yet packaged/signed/published to the Marketplace or validated in remote-container workspaces.
- The Electron application is packageable and its macOS arm64 bundle has passed a local smoke run with the product icon, but it is not signed, notarized, auto-updated, or release-tested on Windows/Linux. PostgreSQL remains an external prerequisite.
- CI verifies migration, code quality, the Observatory bundle composition, and Lighthouse budgets; it does not yet boot all processes for the opt-in load-generating smoke test.

These are interview strengths when stated plainly: the boundaries show what the current evidence proves and what a hosted production architecture must add.

## Agent and MCP boundary

No agent or MCP package is required for the implemented source flows: GitHub uses a purpose-built Octokit adapter, Electron uses a narrow native acquisition bridge, browser input uses the directory API, and VS Code uses the same bounded archive/API workflow. The product intentionally has no autonomous model loop. The optional stdio MCP adapter retrieves bounded completed profiles, findings, scores, architecture summaries, and change impact. It sits outside the deterministic analysis path and has no tools to mutate evidence, scores, source, job state, credentials, AI reviews, or performance targets.
